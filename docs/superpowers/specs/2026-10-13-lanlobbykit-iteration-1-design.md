# LanLobbyKit — дизайн итерации 1

Дата: 2026-10-13
Статус: на ревью
База: итерация 0 (`docs/superpowers/specs/2026-10-13-lanlobbykit-design.md` + deferred-хвосты из ревью)

## Цель

UI-удобство (сплиттеры, сейвы с «Новой игрой»), чистка протокола до стабилизации
публичного API (0.2.0), управление «призраками», цикл «лобби → игра → лобби».

## Не входит

- Миграция хоста, интернет-матчмейкинг, новые таргеты (как в итерации 0).
- CRUD сейвов внутри кита: список сейвов целиком поставляет игра через `scenarios()`.

## Версия

`0.2.0` — провод несовместим с 0.1.0 (новые сообщения `Kicked`, `BackToLobby`,
`RefreshScenarios`; изменённая семантика `Kick`). `LobbyGame`/`LobbyGameUi`/`LobbyClient`
сигнатурно не ломаются (только добавления в enum/flow событий).

## 1. UI: сплиттеры и лейаут

- Используем `HorizontalSplitPane` из `org.jetbrains.compose.splitpane` (compose.components),
  зависимость только в `lobby-ui-compose`.
- Два места: **меню** (профиль | хост/подключение) и **лобби** (игроки+палитра | вкладки).
- Позиция сплиттера в процентах от ширины окна (стартовая 50/50 в меню, ~55/45 в лобби);
  при ресайзе окна обе панели растут/сжимаются пропорционально («в идеале оба одинаково»).
- Минимальная ширина панели по контенту (игроки ~300dp, настройки ~280dp, профиль ~260dp);
  сжали сильнее минимума — контент панели скроллится горизонтально (`horizontalScroll`),
  не ломая соседнюю панель.

## 2. Сейвы: вкладка у хоста

- Вкладка «Сейвы» (только хост): первым пунктом всегда «✚ Новая игра»
  (это `selectedScenarioId = null`, выбрано по умолчанию), ниже — список из `scenarios()`.
- Кнопка «Обновить» во вкладке: хост шлёт `ClientMsg.RefreshScenarios`, сервер через колбэк
  игры перечитывает список и рассылает новый `LobbyState`.
  - Новый серверный хук: `GameSessionHooks` расширяется `suspend fun loadScenarios(): List<Scenario>`
    (default: текущий список из конструктора). `LobbyController` провайдит `game.scenarios()`.
- Если выбранный сейв исчез после refresh — `selectedScenarioId` сбрасывается в null
  («Новая игра»), всем видно.

## 3. Протокол

Новое:
- `ServerMsg.Kicked` — отдельное сообщение; сервер шлёт его при кике вместо
  `Error("kicked")`; клиент маппит в `LobbyEvent.Kicked`.
- `ServerMsg.BackToLobby` — сервер шлёт всем при `ReturnToLobby`; клиент переходит
  `InGame → InLobby` и эмитит `LobbyEvent.LobbyReturned`.
- `ClientMsg.RefreshScenarios` — только хост, только в лобби (иначе `Error("not host")` /
  `"not in lobby"`).

Изменённая семантика:
- `Join` с уже существующим `profileId` = rebind (эквивалент `Rejoin` + обновление ника
  и аватара в слоте). Чинит «второй слот» и легальный флоу «вышел в меню → зашёл снова».
  При смене ника ребиндом проверяется уникальность среди остальных слотов
  (`Error("nick taken")` + закрытие, если занят).
- `SelectScenario`/`UpdateSettings` — только в фазе лобби (`Error("not in lobby")`).

Валидация при Join (сервер-side): пустой/blank ник → `Error("bad nick")`;
аватар > 64 КБ → `Error("avatar too large")`.

## 4. Призраки (disconnected-слоты)

- У слота появляется `disconnectedAtMs` (ставится при обрыве).
- `LobbyServer(..., ghostTtlMs: Long = 5 * 60_000)`: фоновая джоба раз в 10 с удаляет
  слоты с `connected=false` старше TTL — **только в фазе Lobby**. В игре слоты вечны
  (нужны для реконнекта/снапшота).
- При удалении: ник и цвет освобождаются, всем рассылается `LobbyState`
  (+ `PlayerSessionInfo(playerId, nick, DISCONNECTED)` уже шлётся при обрыве; при
  истечении TTL дополнительных событий нет, достаточно LobbyState).
- `ghostTtlMs = 0` отключает чистку.

## 5. Цикл «лобби → игра → лобби»

- `LanLobby.run(game)` становится циклом: контроллер (клиент, сервер у хоста) живёт
  между итерациями. После `game.onGameStarted(...)` (окно игры закрылось) проверяем:
  если за время игры приходило `LobbyEvent.LobbyReturned` — окно лобби открывается снова,
  иначе shutdown.
- Контракт для игр (KDoc на `LobbyGame`): хост инициирует возврат вызовом
  `client.returnToLobby()` из игры; все клиенты получают `LobbyEvent.LobbyReturned`,
  по которому игра **обязана закрыть своё окно** (тогда `onGameStarted` возвращается
  и кит переоткрывает лобби). Закрытие окна игры без `LobbyReturned` = конец сессии.
- Демо-игры: кнопка «В лобби» (только хосту) + авто-закрытие окна по `LobbyReturned` у всех.

## 6. Снапшот при реконнекте — один путь

- `GameSessionHooks.onPlayerRejoin(playerId, send)` остаётся единственной точкой в core;
  атрибуция чинится: сервер шлёт снапшот с `fromPlayerId = hostId` (вместо магии "server").
- `LobbyController` по-прежнему адаптирует его в `game.onPlayerRejoin(playerId, client)`
  через loopback-клиента. Два пути не смешиваются: UI-пользователи видят только
  `LobbyGame.onPlayerRejoin`.

## 7. Полировка (мелочи)

- Аватары в UI: `remember(base64)` вокруг декодирования PNG.
- Snackbar: показ в отдельных корутинах — коллектор событий не блокируется.
- Клиент: `lobbyState` очищается при терминальном дисконнекте (kicked/host dead/leave).
- Сервер: перебор портов ловит только ошибки бинда (не любой Throwable), кламп 65535.
- Сервер: `start()` пересоздаёт shutdown-scope — повторный `start()` после `stop()` валиден.
- lobby-core: `slf4j-api` объявлен явно (api-зависимость) — POM самодостаточен.
- Убрать обёртку `Box_` в `LanLobby.kt`.
- Проверить (и при необходимости починить) персист ника между запусками демо.

## Тестирование (новые/изменённые)

- Протокол: round-trip новых сообщений.
- Сервер: кик шлёт `Kicked` (не Error); `ReturnToLobby` → всем `BackToLobby`, фаза Lobby,
  ready сброшены; `SelectScenario`/`UpdateSettings` в игре → Error; Join-rebind по
  существующему profileId (ник обновился, playerId тот же); TTL-призрак удаляется в лобби
  (TTL маленький в тесте) и не удаляется в игре; пустой ник/большой аватар → Error;
  refresh-сценарии через хук обновляют `LobbyState.scenarios`.
- Клиент: `Kicked` по событию (без строковой магии); `LobbyReturned` → InLobby;
  lobbyState чистится при kicked.
- UI и демо: ручная проверка (два окна: сплиттеры, вкладка Сейвы, «Новая игра»,
  «В лобби» → возврат, рестарт игры из лобби).

## Риски

- `HorizontalSplitPane` — experimental API (`@ExperimentalSplitPaneApi`): зафиксировать
  версию compose.components, обернуть в один наш компонент `SplitRow`, чтобы замена была
  точечной.
- Цикл лобби→игра→лобби: Compose `application {}` дважды в одном процессе уже проверен
  в итерации 0 (лобби → игра), обратный переход — тот же паттерн; риск в утечке окон
  (закрытие game-окна игрой по событию — обязанность игры, задокументирована).
